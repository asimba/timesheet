# Система учёта рабочего времени

Веб-приложение для учёта рабочего времени сотрудников. Сотрудники вносят записи о выполненных работах по проектам, администраторы управляют справочниками и получают сводную статистику с выгрузкой в Excel.

Разворачивается как **один исполняемый файл** (Go + SQLite, без CGO и внешних зависимостей). Все шаблоны, стили и встроенная документация упакованы в бинарник.

---

## Возможности

### Для сотрудника

- Вход по логину и паролю.
- Ведение табеля: добавление, редактирование и удаление записей за последние N дней (по умолчанию 5).
- Переключение месяцев с сохранением контекста (AJAX, без перезагрузки).
- Экспорт своего табеля в Excel за месяц или за все месяцы (отдельный лист на каждый месяц).

### Для администратора

- Управление тремя справочниками: **отделы**, **сотрудники**, **объекты/проекты**.
- Учётные записи сотрудников: автогенерация логина (`user<ID>`) и пароля (8 символов), смена пароля.
- Просмотр и редактирование табелей **любого** сотрудника без ограничения по давности записей.
- Экспорт статистики в Excel:
  - по объектам отдела (с колонкой «Задействованные сотрудники»);
  - по сотрудникам отдела;
  - по конкретному сотруднику.
- Автоматическое резервное копирование БД с ротацией.
- Защита от двойного запуска (lock-файл).
- Журнал событий (входы, изменения, экспорты, ошибки).
- Встроенные руководства: пользователя и администратора.

### Общее

- Роли: `admin` и `employee`.
- Разделение доступа: сотрудник видит только свои записи.
- Хранение паролей сотрудников — bcrypt.
- Экспорт XLSX без сторонних библиотек (свой минимальный OOXML-генератор).
- Локализация интерфейса — русская.

---

## Требования

- Go **1.21+** (для сборки).
- SQLite — **не требуется устанавливать**, используется чистый Go-драйвер `modernc.org/sqlite` (без CGO).
- Любая ОС: Linux, Windows, macOS. Архитектуры: `amd64`, `arm64`.
- Для запуска достаточно одного бинарника и файла `config.json`.

## Быстрый старт

### 1. Клонировать
```
git clone https://github.com/asimba/timesheets.git
cd timeshhets
```

### 2. Скопировать конфигурацию
```
cp config.example.json config.json
```

### 3. Отредактировать config.json — задать логин/пароль администратора

### 4. Собрать
```
go build -o timesheets .
```

### 5. Запустить
```
./timesheets -config config.json
```

Откройте в браузере http://127.0.0.1:8080/ (или адрес/порт из конфига) и войдите под учётной записью администратора.  
#### Первый запуск:
- Создастся base.db и служебные таблицы.  
- Создастся lock-файл base.lock (по умолчанию).  
- Если задан backup_dir — сразу создастся первая резервная копия.  
- Сразу после входа под админом: создайте хотя бы один отдел (иначе нельзя добавить сотрудников), затем проекты и сотрудников.  
#### Конфигурация
Файл передаётся флагом -config (по умолчанию config.json).
```
{
  "listen_addr": "127.0.0.1",
  "listen_port": 8080,
  "admins": [
    { "user": "admin", "password": "CHANGE_ME" }
  ],
  "db_path": "base.db",
  "log_file": "service.log",
  "work_entries_edit_days": 5,
  "backup_dir": "backups",
  "backup_interval_minutes": 30,
  "backup_keep": 7,
  "lock_file": "base.lock"
}
```

| Поле | Назначение | По умолчанию |  
------ | ------ | ------ |  
listen_addr | IP-адрес, на котором слушает сервер | 127.0.0.1  
listen_port | TCP-порт | 8080  
admins | Список администраторов (логин + пароль) | обязателен хотя бы один  
admin_user / admin_password | Альтернатива списку (добавляется в admins) | —  
db_path | Путь к SQLite-базе | base.db  
log_file | Файл журнала (пусто — вывод в stderr) | —  
work_entries_edit_days | Сколько дней назад сотрудник может редактировать записи | 5  
backup_dir | Каталог резервных копий (пусто — бэкапы отключены) | —  
backup_interval_minutes | Интервал резервирования, минут | 60  
backup_keep | Сколько последних копий хранить | 7  
lock_file | Файл блокировки (защита от двойного запуска) | <db_path>.lock

## Использование

### Сотрудник

1. Войти по логину и паролю, выданному администратором.
2. Открыть «Добавить работы»:
   - дата — сегодня/вчера (не старше N дней и не позже завтрашнего дня);
   - время начала;
   - длительность — по времени окончания или в часах/минутах (не более 8 часов за запись);
   - проект из списка;
   - вид работ (обязательно, до 512 символов).
3. Запись сохраняется в табеле и доступна для редактирования в течение N дней.
4. «Экспорт в Excel» — выгрузка за месяц или за все месяцы.


### Администратор

1. Войти под логином из config.json.
2. Открыть вкладку «Группы и отделы» — создать отделы. Рядом с названием отображается количество сотрудников.
3. Вкладка «Объекты и проекты» — создать проекты (наименование + уникальный шифр до 20 символов).
4. Вкладка «Сотрудники» — добавить учётные записи:
   - логин и пароль подставляются автоматически;
   - заполнить ФИО и выбрать отдел.
5. Просмотр табеля сотрудника — кнопка «Табели» в строке сотрудника. Слева от иконки отображается количество записей.
6. Экспорт статистики — кнопки-пиктограммы в строке отдела или сотрудника.

## Резервное копирование

При заданном backup_dir:

- первая копия создаётся сразу при старте;
- затем — каждые backup_interval_minutes минут;
- копия делается через VACUUM INTO (консистентный снимок без остановки записи);
- в backup_dir хранятся только последние backup_keep копий, старые удаляются.

Имена: <имя_БД>.<YYYYMMDD-HHMMSS>.bak.

Восстановление:

1. Остановить приложение.
2. Заменить base.db нужным .bak:
   cp base.db base.db.before-restore
   cp backups/base.20261105-143000.bak base.db
3. Запустить приложение.

Не копируйте .db вручную при работающем процессе — можно получить несогласованный снимок. Только через VACUUM INTO (что и делает встроенный бэкап) или при остановленном приложении.

## Защита от двойного запуска

При старте создаётся lock-файл (lock_file). Если он уже существует — второй экземпляр не запустится и выведет содержимое файла (PID, время старта, хост). По Ctrl+C или SIGTERM lock-файл удаляется автоматически.

После аварийного завершения (kill -9, OOM) файл остаётся. Перед запуском убедитесь, что процесс не работает, и удалите его вручную:

```
rm base.lock
```

## Журнал событий

Все значимые события пишутся в log_file (если задан) или в stderr:

- запуск и остановка, наличие/отсутствие lock-файла;
- ошибки БД;
- входы/выходы (успех и неудача с причиной);
- создание/изменение/удаление групп, проектов, сотрудников, записей табеля;
- экспорты и резервное копирование.

Пример:

```
Сервер запущен: http://192.168.0.120:8080
lock-файл создан: base.lock (pid=12345)
резервирование БД: dir=backups interval=30m0s keep=7
резервная копия БД создана: backups/base.20261106-100001.bak (32768 байт)
пользователь: admin, действие: login, цель: session, результат: ok
```

Рекомендуется настроить logrotate для файла журнала.

## Безопасность

- Пароли администраторов хранятся в открытом виде в config.json — ограничьте права файла:
  chmod 600 config.json
  и не коммитьте его в git (в репозитории только config.example.json).
- Пароли сотрудников — bcrypt-хэши.
- Сессии хранятся в памяти процесса: после перезапуска все пользователи разлогиниваются.
- HTTPS «из коробки» не настроен — рассчитан на локальную/корпоративную сеть. При выносе в интернет поставьте reverse-proxy с TLS (nginx, Caddy, Traefik).
- Администраторы могут редактировать табели без ограничения по давности; сотрудники — только за work_entries_edit_days.

## Сборка

```
go build -o app .
```

Кросс-компиляция (пример: Linux amd64 → Windows amd64, Linux arm64):

```
GOOS=windows GOARCH=amd64 go build -o timesheets.exe .
GOOS=linux   GOARCH=arm64 go build -o timesheets-linux-arm64 .
```

Оптимизированная сборка «под поставку»:

```
go build -trimpath -ldflags "-s -w" -o timesheets .
```
